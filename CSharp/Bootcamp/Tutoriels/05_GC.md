# 05 - GC et retention memoire

[Precedent](04_Generiques.md) | [Sommaire](README.md) | [Suite : ressources](06_Ressources.md)

## Situation et objectif

Votre application cree des objets par requete. Elle utilise un garbage collector, mais sa memoire
augmente quand meme. Pourquoi ? Le GC peut recuperer des objets **inaccessibles**, pas tous ceux
dont l'application n'a plus besoin fonctionnellement.
Prerequis : references, collections et portee d'une variable.

## Exemple : un cache sans politique de sortie

```csharp
for (int identifiant = 1; identifiant <= 3; identifiant++)
{
    CacheSessions.Ajouter(identifiant, new byte[16_384]);
}

Console.WriteLine(CacheSessions.Nombre);
CacheSessions.Retirer(1);
CacheSessions.Retirer(2);
Console.WriteLine(CacheSessions.Nombre);

public static class CacheSessions
{
    private static readonly Dictionary<int, byte[]> Donnees = new();
    public static int Nombre => Donnees.Count;
    public static void Ajouter(int identifiant, byte[] contenu) => Donnees[identifiant] = contenu;
    public static void Retirer(int identifiant) => Donnees.Remove(identifiant);
}
```

Sortie : `3`, puis `1`. Ce sont des nombres d'entrees, pas des mesures d'octets recuperes.

## Reconstituer le chemin de references

1. Le champ statique conserve le dictionnaire pendant la vie de son contexte de chargement.
2. Le dictionnaire conserve ses valeurs, ici les tableaux.
3. La fin d'une iteration ne supprime pas les references contenues dans le dictionnaire.
4. Retirer une entree supprime ce chemin vers le tableau.
5. Sans autre chemin actif vers lui, ce tableau devient eligible a une collecte ulterieure.

Eligible ne signifie pas « detruit maintenant ». Le GC choisit quand collecter.
Un tableau devenu inaccessible peut aussi laisser de la capacite reservee dans le dictionnaire ;
la memoire du processus ne baisse donc pas necessairement immediatement.

## Le modele a retenir

Les racines incluent notamment des references statiques, des references actives des threads
et des handles du runtime. Le GC suit les objets accessibles a partir de ces racines.
La portee ecrite dans le code ne definit pas a elle seule la derniere utilisation decidee par le JIT.

Les generations 0, 1 et 2 favorisent la collecte des objets courts. Survivre a une collecte peut
promouvoir un objet. Les gros objets sont generalement sur le LOH ; le seuil usuel est autour
de 85 000 octets de taille totale, et il est configurable. Ce n'est pas une cible a optimiser a l'aveugle.

Une fuite en code manage est souvent une **retention involontaire** : cache non borne,
historique toujours conserve, closure qui capture un gros objet ou abonnement a un evenement.
Un evenement conserve ses delegates ; un delegate d'instance peut conserver son abonne.

## A vous : imaginer une vraie politique de cache

Pour des sessions de dix minutes, proposer une limite de taille ET une expiration.
Qui declenche l'eviction ? Que se passe-t-il en cas d'acces concurrents ? Une WeakReference suffit-elle ?

<details>
<summary>Correction raisonnee</summary>

Une politique plausible combine une expiration, un budget de taille et une eviction.
Dans une application reelle, un composant de cache existant evite de reinventer la synchronisation
et l'entretien. Les tailles doivent etre estimees suivant les conventions du composant choisi.
Une WeakReference autorise la disparition de la valeur selon les besoins du GC : elle ne garantit
pas une duree de session et ne remplace donc pas un stockage de session fiable.

Il faut aussi distinguer une session qui doit survivre a un redemarrage d'un resultat recalculable.
Leur stockage et leur politique de perte ne sont pas identiques.

</details>

## Diagnostiquer avant de modifier

Observer d'abord le debit d'allocations, la taille du heap et les collections avec les outils .NET
adaptes a l'environnement. Comparer ensuite deux captures sous une charge comparable.
Dans un dump, chercher les types qui grossissent et le chemin de racines qui les conserve.
Ne pas conclure a une fuite uniquement parce que le gestionnaire des taches montre une valeur elevee.

Ajouter `GC.Collect()` dans les requetes ne corrige pas un dictionnaire qui conserve les objets.
Le GC n'est pas non plus responsable de fermer rapidement tous les fichiers : sujet suivant.

## Verification

- Un objet encore accessible peut-il etre inutile au produit ? Oui, c'est une retention possible.
- Quitter une boucle garantit-il une collecte ? Non.
- Une diminution du nombre d'entrees impose-t-elle une baisse immediate de la memoire du processus ? Non.

Il n'y a pas de nouveau test automatique ici : savoir dessiner le chemin
`racine -> dictionnaire -> tableau` et proposer une politique de duree de vie est le travail demande.
